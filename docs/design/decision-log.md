# Decision log

Smaller decisions, made with the owner during planning or by the orchestrator during the build. Each row says what was decided and why.

| ID | Date | Area | Decision | Why |
|---|---|---|---|---|
| D1 | 2026-11-01 | Process | A change that meets the definition of done may be committed straight to `gtnh`. Parallel or long work happens on its own branch in a worktree. It is verified after merging `gtnh` in, merged with `--no-ff`, then the branch and worktree are removed. `gtnh` is pushed at roadmap gates and when the owner asks; `1.20` only tracks upstream | Owner's choice (TrainHorizons style); one revertible merge per parallel feature without a pull request per change |
| D2 | 2026-11-01 | Spec | The upstream behavior spec is area sheets plus a bug register: one sheet per system, with behavior, every number and tunable, asset formats and suspected bugs, and no per-entity pixel or UV detail ([original-spec/CONVENTIONS.md](../original-spec/CONVENTIONS.md)) | Owner's choice. Code is portable under [0001](0001-port-policy-and-licensing.md), so the spec is the test contract and the bug list, not a clean-room substitute for the code |
| D3 | 2026-11-01 | Tooling | `tools/semantic-search/` indexes this repository and every source and asset file on the local `1.20` branch, read from git without a checkout. Upstream hits are written `1.20:<path>` | Agents find upstream behavior by meaning before they know class names; one index serves every worktree |
| D4 | 2026-11-01 | Process | Builds, tests and Minecraft runs happen on the shared build server, never on a development laptop. Local Gradle, when unavoidable, runs one build at a time with `--no-daemon --max-workers=2 -Dorg.gradle.jvmargs=-Xmx2g`, and never `--stop`. Host details stay out of the repository | The development laptop has too little memory for Gradle daemons and Minecraft alongside the editor; the same rule holds in the owner's other mods |
| D5 | 2026-11-01 | Docs | [CONTRIBUTING.md](../../CONTRIBUTING.md) holds the binding rules (must and should). The skills in `.claude/skills/` hold the how-to. [CLAUDE.md](../../CLAUDE.md) is a thin map to both. The specs are `docs/original-spec/` (upstream) and `docs/new-spec/` (how this mod differs and fits the pack) | One home per kind of rule; the same split as the template the skills come from |
| D6 | 2026-11-01 | Code layout | Root package `com.tuxprogrammer.lostcities` with `asset` and `layout` as pure Java (no Minecraft types), `worldgen` as thin glue writing through a chunk-buffer interface, `client` for every client-only class, and `compat.<mod>` for optional integrations ([CONTRIBUTING § Architecture](../../CONTRIBUTING.md#architecture)) | World generation logic becomes unit-testable and deterministic by construction; static checks can enforce the boundaries by package |
| D7 | 2026-11-01 | Testing | World generation is tested in four layers: unit tests on layout and assets; golden-chunk hashes for fixed seeds, profiles and coordinates; headless worldgen scenarios on fresh worlds (no cascading generation, time budget, determinism across two worlds); and real-pack runs at the gates | Upstream relies on human visual checks only (its `AGENTS.md`); a backport across five Minecraft versions needs automated proof that layouts stay stable and correct |
| D8 | 2026-11-01 | Gates | The alpha gate's owner review is light: a screenshot set from the real pack, reviewed asynchronously. The interactive review (play sessions and back-and-forth on GTNH integrations and advanced features) happens in the beta phase ([ROADMAP](../ROADMAP.md)) | Owner's choice; alpha proves the RWG overlay works, beta is where integration depth gets judged |
